## Где лог и как откатить

**Лог.** Каждая выполненная команда и её вывод пишутся в
`/var/log/usfc.log`, даже когда на экране только спиннер. После 5 МБ лог
переносится в `/var/log/usfc.log.1`. Чтобы видеть вывод сразу на экране,
запустите с `--verbose`.

**Откат.** Перед каждой правкой системного файла usfc кладёт копию в
`/var/backups/usfc/<метка>`. Метка печатается в конце прогона.

1. Посмотрите снимки:

   ```bash
   sudo usfc backups
   ```

2. Верните нужный:

   ```bash
   sudo usfc restore 20261023-040000-3691
   ```

   Замените `20261023-040000-3691` на метку из списка.

Перед откатом снимается ещё один снимок, так что откат тоже можно
откатить. Файлы, которых до usfc не было, при откате удаляются. Пакеты и
сервисы откат не трогает — только файлы. Команды удаления по каждому пункту
— на экране `I` в меню.

## Вход по паролю работает после SSH hardening

**Симптом.** Пункт 18 показывает «! пароль не выключен (перебит другим
конфигом)» или «! root-логин разрешён (перебит другим конфигом)».

**Причина.** sshd берёт первое значение каждого ключа. Если файл
провайдера в `/etc/ssh/sshd_config.d/` сортируется раньше файла usfc или
ключ задан в `sshd_config` до строки `Include`, побеждает он.

1. Посмотрите, что sshd применяет на самом деле:

   ```bash
   sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin|kbdinteractive'
   ```

2. Найдите, кто задаёт ключ:

   ```bash
   sudo grep -rn -i 'PasswordAuthentication' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
   ```

3. Примените пункт **18 «SSH hardening»** заново: `sudo usfc`. Он найдёт
   строки-конфликты, покажет «файл:строка → значение» и предложит
   закомментировать их со снимком.

`usfc audit` сообщает о таком файле как о находке `ssh.dropin_order`.

Если на сервере остался `10-hardening.conf` от 4.x, пункт показывает
«! старый 10-hardening.conf». Применение пункта заменит его на
`00-usfc-hardening.conf` — см. [MIGRATION-5.md](MIGRATION-5.md#ssh-hardening-новый-файл-drop-in).

## SSH hardening не применился или откатился сам

До любых изменений пункт заводит временный ключ и проверяет вход по нему на
`127.0.0.1`. Не прошло — hardening не запускается. После рестарта sshd пункт
сверяет все ключи через `sshd -T`; расхождение — откат, пароль остаётся
включённым. Это защита, а не поломка: причину пункт печатает, она же в логе.

Частые причины:

- **sshd слушает не все адреса.** Пункт пишет «sshd слушает не все адреса
  (ListenAddress) — самопроверке нужен 127.0.0.1». Добавьте
  `ListenAddress 127.0.0.1` или уберите ограничение и примените пункт снова.
- **Чужой файл перебивает ключи.** Пункт называет файл-победитель — см.
  [предыдущий раздел](#вход-по-паролю-работает-после-ssh-hardening).
- **Нет обычного пользователя.** Под прямым root пункт неприменим: вход
  под root он же и закрывает. Создайте пользователя пунктом **1**.

## Перенос SSH-порта не завершён

Статус пункта: «! порт: перенос 22 → 2222 не завершён». Это первый шаг
переноса: sshd слушает оба порта, UFW разрешает оба.

1. Проверьте вход на новом порту со своей машины:

   ```bash
   ssh -p 2222 user@server
   ```

   Замените `2222`, `user` и `server` на свои значения.

2. Закройте старый порт — повторите ту же команду или ответьте «да» на
   вопрос в меню:

   ```bash
   sudo usfc apply sshhardening --ssh-port 2222
   ```

Передумали — перенесите порт обратно тем же способом: `--ssh-port 22`.

Если перенос не начинается и пункт пишет «ListenAddress с явным портом
сильнее Port», уберите порт из строк `ListenAddress` в `sshd_config` и
повторите.

## Своп без приоритета

**Симптом.** `swapon --show` показывает у swap-файла приоритет `-2` (или
любой, кроме `10`), и своп на диске используется раньше zram.

1. Проверьте:

   ```bash
   swapon --show
   grep -v '^#' /etc/fstab | grep swap
   ```

   В четвёртом поле строки свопа должно быть `pri=10`.

2. Откройте меню и выберите пункт **17 «ZRAM + swap + earlyoom»**. При
   такой проблеме он показывает «! приоритет свопа не записан в fstab» и исправляет
   строку, не выключая zram. Пункт понимает строки с `defaults`,
   `sw,nofail`, `pri=N`, `UUID=` и `LABEL=`.

Своп не выключается для исправления, если занятое в нём не помещается в
свободную память, — пункт скажет об этом прямо.

## Порты Docker открыты, хотя UFW их не разрешает

**Причина.** Docker публикует порты (`-p 8080:80`) собственными правилами
iptables в обход цепочек UFW. `usfc audit` показывает это как
`ports.docker`.

Подчините порты контейнеров UFW:

```bash
sudo usfc firewall docker on
sudo usfc firewall --allow 8080
```

После `docker on` снаружи к контейнерам проходит только то, что
разрешено через `usfc firewall --allow`. Работает для IPv4 и
iptables-бэкенда Docker. Вернуть как было — `sudo usfc firewall docker off`.

## Уведомления в Telegram не приходят

1. Отправьте тестовое сообщение напрямую:

   ```bash
   sudo /usr/local/sbin/usfc-notify "проверка"
   ```

   Без `--bg` скрипт печатает ответ Telegram при ошибке (токен в нём
   заменён на `***`).

2. По ответу:
   - `Unauthorized` — неверный токен. Примените пункт **15** заново.
   - `chat not found` — неверный `chat_id`, или вы не написали боту
     `/start`, или бот не добавлен в канал.
   - таймаут — сервер не достучался до `api.telegram.org`: проверьте
     исходящий HTTPS.
3. Сбои фоновых отправок (вход по SSH, бан) пишутся в системный журнал:

   ```bash
   sudo journalctl -t usfc-notify --since today
   ```

Настройки лежат в `/etc/usfc/notify.conf` (права `600`). Уведомление о
входе по SSH отправляется в фоне и не задерживает вход, даже если сети нет.

## btop: «~/.config could not be created»

**Причина.** В 4.x пункт fastfetch создавал `~/.config` от имени root, и
программы пользователя не могли писать в свой же каталог.

В 5.0 каталоги в домашнем каталоге создаются от имени пользователя, а
уже сломанный `~/.config` чинится при применении любого пункта, который
туда пишет: `cli`, `fastfetch`. Исправить вручную:

```bash
sudo chown "$USER": ~/.config
```

## Установка висит на «Could not get lock»

На только что созданном сервере `apt-daily.timer` запускает
`unattended-upgrades`, и тот держит блокировку dpkg минутами. usfc ждёт её
до 300 секунд. Увеличить ожидание:

```bash
sudo USFC_APT_LOCK_TIMEOUT=900 usfc apply web
```

## Команда завершается с кодом 2

Код `2` — ошибка в аргументах или файле ответов. Сообщение над кодом
говорит, что именно не так. Частые случаи:

- **Старая форма 4.x** (`--apply`, `--audit`, `--list`, `--backups`,
  `--restore`). usfc печатает готовую новую строку. Таблица замен — в
  [MIGRATION-5.md](MIGRATION-5.md#было--стало).
- **Флаг для пункта, которого нет в списке**: `--swap` без `zram`,
  `--allow` без `ufw`. Добавьте пункт или уберите флаг.
- **Неизвестный ключ или неверное значение в файле ответов**. Сообщение
  называет файл и строку: `node.conf:4: неизвестный ключ UWF`.
- **Опция не от своей команды**: `--json` работает только с `audit`.

Полный справочник — в [CLI.md](CLI.md).
